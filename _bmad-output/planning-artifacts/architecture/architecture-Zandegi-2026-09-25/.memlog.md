- (constraint) The current pnpm monorepo is canonical; legacy is reference and extraction source, not a second application to preserve in parallel.
- (direction) Deliver both a terse architecture spine and an implementation-ready legacy extraction and repair plan for the next developer.
- (event) Architecture coaching run activated.
- (direction) User selected the Coaching path; surface load-bearing alternatives and decide them together.
- (constraint) CLAUDE.md and SPEC.md bind progression to an append-only event ledger with compensating corrections; Character, DomainStat, Streak, and Wallet are replayable projections.
- (constraint) @zandegi/core remains pure and deterministic with no I/O or framework imports; model-generated content cannot assign progression-affecting numbers.
- (constraint) The current pnpm monorepo has implemented core, AI generation, celebrations, and the web experience; db, api, economy, tools, and integrations remain scaffolds, while legacy is extraction reference only.
- (question) Decide whether event sourcing governs only progression and economy facts or expands to broader application state; current recommendation is a modular monolith with a functional core/imperative shell and a bounded event-sourced ledger.
- (decision) ADOPTED: Use a modular monolith with a functional core and imperative shell. Event sourcing governs progression and economy facts; ordinary operational and authored records use conventional relational state. Binds data mutation, persistence, and package boundaries. Prevents incompatible CRUD mutation of replayable progress without imposing event-sourcing machinery on every entity.
- (decision) ADOPTED: @zandegi/api owns cross-capability use cases and transaction boundaries. Web, mobile, admin, and background entry points call application use cases there; tRPC handlers remain thin. Capability and infrastructure packages never import @zandegi/api. Binds orchestration and dependency direction. Prevents each entry point from ordering AI, ledger, projection, economy, tools, and integration work differently.
- (direction) The existing apps/web API route importing @zandegi/ai directly is a prototype seam to migrate behind @zandegi/api, not a precedent for new workflows.
- (decision) ADOPTED: Use hybrid consistency. A single PostgreSQL transaction appends the immutable domain event, updates immediate user-visible projections (Character, DomainStat, Streak, Wallet, XpAward), and writes an outbox record. Inngest processes leaderboards, crew feeds, notifications, analytics, and external effects asynchronously and idempotently. Binds completion latency and consistency. Prevents both visibly stale earned state and synchronous coupling to non-critical side effects.
- (decision) ADOPTED: All ledger events use shared, versioned schemas in @zandegi/core and a standard envelope carrying identity, subject, timing, correlation, causation, and idempotency data. Only @zandegi/api appends through the ledger interface; raw event inserts are forbidden. Consumers explicitly handle stored versions, unknown versions fail closed, and corrections are compensating events. Binds event producers and consumers. Prevents incompatible payloads, duplicate awards, unreadable history, and rewritten audit records.
- (decision) ADOPTED: @zandegi/core owns fair-progression rules and shared contracts, including XP, levels, ranks, rarity, goal types, safety invariants, and event schemas. @zandegi/economy owns Shards, Crowns, shops, seasons, subscriptions, and entitlements while remaining free of persistence. @zandegi/db stores data without deciding rewards; @zandegi/api coordinates actions and authorization; @zandegi/ai creates content without awarding progression or spending currency; apps contain no business rules. Binds shared-data and policy ownership. Prevents competing reward calculations and commercial policy leaking into clients or storage.
- (decision) ADOPTED: Mission generation is request-scoped and streamed; client disconnect aborts all model work and retry starts a new run. It is not a durable or resumable background job in the first release. Binds AI execution and failure recovery. Prevents abandoned generation cost and avoids maintaining separate visitor and signed-in job systems before usage proves the need.
- (decision) ADOPTED: Before signup, the server creates a temporary guest principal bound to a secure cookie. Guest missions and first-XP events use the same trusted ledger path as registered users. Signup atomically and only once links the guest principal to the Clerk-backed account; stale unclaimed guest data expires. Clients never submit trusted XP, balances, or projection totals. Binds anonymous onboarding and identity merge. Prevents fake first XP, client tampering, duplicated claims, and loss of pre-signup progress.
- (decision) ADOPTED: Use the low-operations managed deployment path: Vercel Node functions with Fluid Compute for web/API, Neon Postgres, Upstash Redis Global for disposable cache and rate-limit state only, Inngest serve endpoint for background work, and Clerk for identity. Co-locate Vercel, Neon, and the Upstash primary in Sydney. Isolate development/preview from production; add permanent staging only when needed. Binds deployment and infrastructure. Prevents premature self-hosting work, cross-region database latency, and preview access to production data.
- (decision) ADOPTED: Begin on free or usage-based tiers with budgets and alerts; upgrade services when measured limits, reliability, compliance, or team needs require it. This optimizes total cost including engineering time, not the absolute minimum server rental. Binds launch cost posture. Prevents buying production-scale capacity before demand and prevents unbounded pay-as-you-go surprises.
- (version) Verified 2026-10-02 against official provider sources: Vercel Fluid Compute supports the request duration and Sydney region; Neon exposes Sydney Postgres and branching; Upstash Global supports Sydney primary and serverless REST; Inngest supports serve() in Vercel; Clerk separates development and production instances. Recheck exact plan limits and prices before launch.
- (decision) ADOPTED: Use private Vercel Blob storage for v1 user evidence. Apps request uploads and authorized reads through @zandegi/api; Postgres stores ownership and verification metadata only. A narrow storage interface prevents provider-specific URLs or SDK types from entering domain contracts, preserving an S3 migration path. Health and financial integration data never enters the evidence store. Binds evidence storage and access. Prevents public-by-link evidence, database blob storage, and premature AWS/KMS complexity.
- (version) Verified 2026-10-02: Vercel Blob supports private stores, client uploads, selectable Sydney storage, AES-256 encryption, and a Hobby allowance of 1 GB storage and 10 GB transfer. Private storage is currently beta; revisit before handling regulated documents or making stronger availability/compliance commitments.
- (decision) ADOPTED: Web and Expo mobile share @zandegi/core rules, API contracts/client, validation schemas, design tokens, and analytics names; they do not share complete screens or platform controls. Web uses web components and mobile uses native Expo components. Binds cross-platform reuse. Prevents duplicated business rules while avoiding lowest-common-denominator UI and React Native Web coupling.
- (decision) ADOPTED: Mobile provides bounded offline support. Cached missions and steps remain readable; eligible completion commands queue locally with client-generated idempotency IDs. Rewards remain visibly pending until @zandegi/api validates and records them after reconnect. Integration-verified actions cannot finalize offline. Binds mobile synchronization and reward trust. Prevents duplicate awards and client-authoritative XP while preserving the daily loop without connectivity.
- (decision) ADOPTED MVP SCOPE: Defer all third-party integrations, including health, fitness, GitHub, banking, and external calendar sync. The internal Zandegi scheduler remains in scope. Keep @zandegi/integrations as an unimplemented boundary only; select providers and detailed data handling when an integration is promoted into scope. Binds MVP scope and sequencing. Prevents connector complexity from delaying the core mission-to-effort-to-reward loop.
- (question) Revisit external integration architecture only when the first integration is selected; then define token ownership, normalized verification facts, deletion, encryption, and AI exclusion.

Legacy contributes compatible pure algorithms, seed ideas, copy, and characterization cases only; each is reimplemented against current core, API, and ledger contracts. No runtime import may cross from current code into legacy, and legacy schema, NextAuth, routes, mixed I/O services, direct projection mutations, old economy, and generic progress percentages are rejected. Remove legacy only after every capability is extracted or explicitly declined. Binds migration and dependency rules. Prevents revival of incompatible architecture while preserving proven behaviour.
